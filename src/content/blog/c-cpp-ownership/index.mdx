Programs create values and acquire resources while they run. Some values only
need to exist for one function call. Others need to survive until the program
explicitly decides it is done with them. Memory management is the bookkeeping
that makes sure each value has somewhere to live and that its resources are
eventually released.

We will look into lifetimes as they apply to variables and resources.
The stack is location of memory that the program can allocate fix sized chunks of memory on.
These regions of memory have a lifetime, often the enclosing scope they are in.

```c
void process(void) {
    int data[1024]; // <--| `data`'s lifetime starts here
                    //    |
} // <--------------------| `data` is cleaned up when `process` returns, ending its lifetime
```

Here, the region of memory allocated to `data` is valid for as long as `data` is in scope.

```c
void process(void) {
    int data[1024]; // <-------| `data`'s lifetime starts here
    {                       // |
        int data2[1024]; // <-----| `data2`'s lifetime starts here
                            // |  |
    } // <------------------------| `data2`'s lifetime ends here
                            // |
} // <-------------------------| `data`'s lifetime ends here
```

We see that the region of memory that is allocated to `data` and `data2` matches the lifetime that of the variable that
holds that memory. When the variable is in scope, the memory is valid to use.

This is true for stack allocated memory, but not guaranteed for dynamically allocated memory.

```c
void do_something(int *data);
void process(void) {
    int *data; // <---------------------------| `data`'s lifetime starts here
    data = malloc(1024 * sizeof(*data)); // <---| dynamically allocated memory's lifetime starts here.
                                           // | |
    free(*data); // <---------------------------| the memory's lifetime ends, but `data` is still in scope
                                           // |
    do_something(data);                    // | Here we use the memory that was held by `data` after its lifetime ended (BAD)
} // <----------------------------------------| `data`'s lifetime ends here
```

This disconnect is where most bugs happen. Either the memory's lifetime ends too soon, so we end up using the memory
after we've given it back to the OS, or the variable's lifetime ends so we can't free the memory again.

We can re-write the example so they mostly line up to fix it in this case, but it will get more difficult as our
function gets more complex.

```c
void do_something(int *data);
void process(void) {
    int *data = malloc(1024 * sizeof(*data)); // <---| `data`'s and memory's lifetime start here
                                                  // |
    do_something(data);                           // | `data` and memory still have valid lifetimes
                                                  // |
    free(*data); // <--------------------------------| the memory's lifetime ends, and `data` will go out of scope soon
}
```

Let's see a more complex example


```c
struct Request { /* ... */ };
int* get_data() {return malloc(...);}
Request parse_data(int *data);
Request process(void) {
    int *data = get_data(); // <-----------| `data`'s and memory's lifetime start here
                                        // |
    Request request = parse_data(data); // |
                                        // |
    free(*data); // <----------------------| the memory's lifetime ends, and `data` will go out of scope soon

    return request;
}
```

Is this program valid? We can't tell, because we don't know the lifetime of request. If `request` points inside of
`data`'s memory, then when we free `data`, `request` will be storing invalid (freed) memory. If request copied the data
it needed into a new allocation, then this is fine as long as request's memory is freed later. In C, your best option is
to document these things in the contract of the function.

```c
/// Caller is responsible for freeing returned data with `free`.
int* get_data();
/// Return value's lifetime is tied to that of `data`.
Request parse_data(int *data);

// or

/// Caller is responsible for freeing returned request with `request_free`.
Request parse_data(int *data);
```

We'll take a look at a strategy for making working with dynamically allocated memory in C easier, but let's take a look
at what tools C++ gives us for managing dynamic memory allocations.

## C++

C++ allows the programmer to allocate and free memory dynamically with the `new` and `delete` keywords. These are almost
identical to `malloc` and `free`.


This is commonly called "stack allocation," and is convenient for automatically managing memory. However, stack allocation has some limitations.
- Memory on the stack must have a fixed size at compile time[^1]
- Memory on the stack must be able to fit in the available stack space, which is usually 8-16 Mib

Dynamic allocation is useful when a value is too large for
automatic storage, its size is not known in advance, or it must outlive the
scope that created it.

You can return data from functions, and most compilers will avoid copying the data (called copy elision). This will let the value on the stack escape to the stack above it.

The rest of this article builds a mental model for dynamic resources around
three questions:

1. **Ownership:** who is responsible for releasing the resource?
2. **Borrowing:** who can access the resource without becoming responsible for managing
   it?
3. **Lifetime:** for how long is that access valid?

We will begin with manual ownership in C, see how C++ makes ownership executable
through RAII, and then return to C to group related lifetimes with an arena.

## Ownership in C

Keeping track of memory manually can be difficult, but ownership gives us a
useful rule: every resource has an _owner_, and the owner is responsible for
releasing it.

```c
int main(void) {
    int *data = malloc(1024 * sizeof(*data)); // <--| the memory's lifetime starts here
    if (data == NULL) {                       //    |
        return 1;                             //    |
    }                                         //    |
                                              //    |
    // Use data...                                  |
                                              //    |
    free(data); // <--------------------------------| lifetime ends here
}
```

Here, we designate `data` as the owner of the allocation. C does not record that
relationship in the pointer's type; it is a contract established by the program.
That contract matters as soon as we introduce another pointer.

```c
int *data = malloc(1024 * sizeof(*data));
int *data2 = data;

free(data);
// free(data2); // This would free the same allocation twice.
```

Copying the pointer did not copy the allocation. Both pointers contain the same
address, but only one of them can be responsible for calling `free`. In this
example, `data` remains the owner and `data2` is a non-owning alias.

Function boundaries make this distinction especially important. An API should
make it clear whether a function only uses an allocation or takes responsibility
for releasing it. If a function returns some resource, it should make it clear whose job it is to release the resource, and how.

```c
// Borrows the allocation for the duration of the call.
void inspect_data(const int *data, size_t length);

// Takes ownership and eventually releases the allocation.
void consume_data(int *data) {
    // Use data...
    free(data);
}

int main(void) {
    int *data = malloc(1024 * sizeof(*data));
    if (data == NULL) {
        return 1;
    }

    inspect_data(data, 1024);
    consume_data(data);

    // `data` no longer points to a live allocation here.
}
```

C has no built-in distinction between an owning pointer and a pointer that
borrows from an owner. Projects communicate the distinction through naming,
comments, documentation, and conventions. Every return path must still uphold
the contract, which becomes harder as a program grows.

## Making Ownership Concrete with RAII

C++ has a language feature called _destructors_ which make manage resources less error-prone.
When you create a class, you can specify a function that will be called when a value goes out of scope.

This can be used to tie the lifetime of a resource to the lifetime of a variable. We can allocate the resource in the
constructor and deallocate it in the destructor.

## Lifetimes

A borrow is safe only while the value it refers to is alive. A value's
_lifetime_ is the portion of program execution during which that value exists

## Grouping Lifetimes with Arenas

Per-object ownership gives precise control, but some objects naturally share a
lifetime. A parser might create many syntax nodes that all become useless when
parsing finishes; a game might create temporary data that all becomes useless at
the end of a frame. An _arena_ makes that relationship explicit by owning a
larger region from which many smaller allocations are made.
