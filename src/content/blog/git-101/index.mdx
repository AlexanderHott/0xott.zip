This article serves as an introduction to Git. It starts with a brief history,
introduces a mental model for how to think about Git, and ends with an exercise
going over the most common scenarios and how they relate to the mental model.

# A Brief History

## What is Git?

Git is a set of tools for building a _distributed version control system_.

That phrase makes more sense read backwards:

- It is a _system_: a way of doing things.
- It is for _version control_: keeping a useful history of something, usually
  code.
- It is _distributed_: it is designed to work across multiple people and
  computers.

It provides the mechanisms, but you decide the patterns and rules for using them.

Distributed version control systems let you view old snapshots, work on changes
in parallel, and answer questions about the history of your content: who wrote
this, who last changed this line and why, what did this file look like last
week, when was this bug introduced, what changed between these releases, and
when was this exact string added or removed?

## Why Git?

Git was created in 2005 by Linus Torvalds after the Linux kernel project lost
access to BitKeeper, the distributed version control system it had been using.
None of the existing solutions met the needs of the Linux kernel, so he wrote
his own. Since then, the project has been maintained by Junio Hamano.

Today, Git is popular because it is free, fast, and flexible. It supports
simple single-person projects and the complex workflows used by large companies.
Much of the world's code lives on GitHub, which uses Git as the underlying
version control system. GitHub's pull request workflow is the backbone of modern
software collaboration, so Git became the de facto default.

# Mental Model

To better understand how to use Git and how to speak about its different operations,
it's very useful to understand how Git works under the hood.

## How does Git work?

Git's core data model is made of two types of things: _objects_ and _refs_.
Once those are clear, commands like `commit`, `branch`, `merge`, and `rebase`
become much easier to reason about.

### Git's core data model

At its core, Git tracks files and folders. It stores the contents of a file in a
_blob_. The blob does not know the file's name. A _tree_ gives blobs their names
and arranges them into folders. This means two files with the same contents can
use the same blob. It also means Git does not track empty folders.

In pseudocode, that might look like

```typescript
type Blob = List<Byte>;

type Tree = Map<String, Blob | Tree>; // name -> file/folder
```

Here is an example root tree that Git could track:

```
python_project/   (root tree)
├── src/          (tree)
│   └──  main.py  (blob)
└── README.md     (blob)
```

Git tracks history by taking snapshots of the root tree. Each snapshot becomes
more useful when it also records who made it, when it was created, a short
message about why it exists, and which previous snapshots it is based on. That
whole bundle is called a _commit_.

```typescript
type Commit = {
  snapshot: Tree;
  createdAt: Datetime;
  message: String;
  author: String;
  parents: List<Commit>;
};
```

Blobs, trees, and commits are all _objects_. Objects are identified by a hash of
their contents. A hash function is a mathematical function with some special
properties, but conceptually it produces a fingerprint of its input. This is
useful because we can store and look up objects based on their fingerprint,
which is usually much smaller than the entire object. By default, Git uses the
SHA-1 algorithm and displays object IDs as 40-character hexadecimal strings,
e.g. `2683ad5152dd330f1faabc9911829fb00b803302`.

<Aside title="A note about object IDs">
A hash is not guaranteed to be mathematically unique, although collisions are
extraordinarily unlikely in normal use. Git hashes an encoded representation
containing the object's type, size, and content. Git also supports SHA-256
repositories, whose object IDs are displayed as 64 hexadecimal characters.

See https://www.youtube.com/watch?v=k0oG_jt6l7Q, shoutout https://boot.dev (not sponsored)
</Aside>

So really, a commit looks like this

```typescript
type ObjectId = Bytes;

type Commit = {
  snapshot: ObjectId;
  // ...
  parents: List<ObjectId>;
};
```

but you should still think of a commit as keeping track of the snapshot tree and
parents.

Git keeps track of all these objects in an *object store*, a database mapping the
object's hash (fingerprint), to the object itself.

```typescript
type Object = Blob | Tree | Commit;

const objects: Map<ObjectId, Object>; // object hash -> object
```

<Aside title="What about tags?">
Git has a fourth object type, the annotated tag object, which this simplified
model omits. Tags don't get updated when you commit, so they are useful for
marking things like specific versions, like `v1.2.3`. TODO: improve, plus git list tag config trick
</Aside>

Objects are immutable: once created, they do not change. If content or history
changes, Git writes new objects with new hashes.

Hashes are useful to Git, but names are easier for people to remember. Git calls
these names _refs_. A ref points to an object or to another ref. Unlike an
object, a ref can change what it points to.

```typescript
type RefName = String;
type RefTarget = ObjectId | RefName;

const refs: Map<RefName, RefTarget>;
```

For example, a branch is a ref that points to a commit. `HEAD` is a special ref
that tells Git which branch you are currently working on. For now, you can think
of it as pointing to your current branch. We will see both refs in the diagrams
below.

### Working tree, staging area, and repository

A _repository_ is simply the collection of objects and refs. Git stores this
in the `.git` folder that marks the root of the repository.

The _working tree_ is the files and folders you can see and edit.

The _staging area_ is the snapshot you are preparing for the next commit.

Most "everyday" commands move information between those places:

- `git add` copies content from the working tree into the staging area.
- `git commit` turns the staged content into a commit and moves the current
  branch (ref) to that new commit.
- `git switch` changes which branch `HEAD` (ref) points at.
- `git merge` combines work from another branch with the current branch.
- `git rebase` moves a series of commits to a new starting point.

We will cover these all in more detail in the following example.

### Branching

A branch is a movable name that points to a commit. Following that commit's
parents gives us the branch's history. Here, `main` points to `C`, and the
history leading to `C` is `C` -> `B` -> `A`.

Creating a branch does not copy the project. It creates another name pointing
at a commit.

`git switch` is a fairly new subcommand. In older versions of Git, you would use
the `git checkout` subcommand to switch and create branches, but `checkout` did
so many other things that Git added `switch` specifically for switching and
creating branches.

Creating the branch `fix` does two things:

- creates a new ref called `fix`
- points `fix` at the current commit, `C`

```sh
git switch -c fix
```

```bash
git log --oneline --graph --decorate --all
```
```
* 7610ec3 (HEAD -> fix, main) C: Add print to main.py
* e114851 B: Add main.py
* 09da7ce A: Add readme
```

We can see that we currently have `fix` checked out, and both main and fix are pointing at C.

### Integration

We now have work on two branches that we want to keep: `main` has commit `E`,
and `fix` has commit `D`. We need to combine them. Git calls this _integrating_
changes and has two common ways to do it: _merging_ and _rebasing_. We will
start with merging.

The simplest merge is a _fast-forward_. Imagine that `main` still pointed to
`C` and only `fix` had moved forward to `D`. Git could update `main` by moving
its pointer from `C` to `D`. No new commit would be needed.

<FastForwardSvg width="100%"/>

Our branches cannot be fast-forwarded because both names moved after `C`:
`main` moved to `E`, while `fix` moved to `D`. Git compares the changes from
`C` to `E` with the changes from `C` to `D` and tries to combine them. If it
succeeds, it saves the result in a new _merge commit_. The merge commit points
back to both `E` and `D` as its parents.

In this example, the branches changed different lines, so Git can combine the
changes automatically. TODO: more on this auto merge

```sh
git merge fix -m "F: Merge branch 'fix'"
```
```
Auto-merging src/main.py
Merge made by the 'ort' strategy.
 src/main.py | 3 ++-
 1 file changed, 2 insertions(+), 1 deletion(-)
```

Now we can delete the `fix` branch. This deletes only the name `fix`, not the
commits. Commit `D` is still part of the history because the new merge commit
points back to it.

```bash
git branch -d fix
```

The merge commit has two parents:


### Rebasing

Merging combined `main` and `fix` by creating a commit with two parents. In the
next example, _rebasing_ will combine work differently: it will recreate
commits from one branch after the latest commit on another branch.

Create a feature branch:

```sh
git switch -c feature
```

Start by changing the string in the print statement again:

```diff
 def main():
-    print("hello git")
+    print("Hello, git!")

 if __name__ == "__main__":
     main()
```

Stage and commit it:

```sh
git add -A
git commit -m "G: Make print fancy"
```

Then add another line:

```diff
 def main():
     print("Hello, git!")
+    print("Hello, rebase!")

 if __name__ == "__main__":
     main()
```

Stage and commit that too:

```sh
git add -A
git commit -m "H: Add more printing"
```

While that work is happening, `main` can keep moving:

```sh
git switch main
```

Change `README.md`:

```markdown
# Amazing project
```

Stage and commit it:

```sh
git add -A
git commit -m "I: Update readme"
```

Before rebasing, the graph looks like this:

```text
* <I> (HEAD -> main) I: Update readme
| * <H> (feature) H: Add more printing
| * <G> G: Make print fancy
|/
*   <F> F: Merge branch 'fix'
```

The `feature` branch started at `F` and added `G` and `H`. While that happened,
`main` added `I`. Rebasing recreates the changes from `G` and `H` after `I`, as
if the feature work had started from the latest commit on `main`.

<RebaseSvg width="100%" />

Now replay `feature` on top of `main`:

```sh
git switch feature
git rebase main
```

After rebasing, `G` and `H` have been recreated as `G'` and `H'`. Their changes
are the same, but they have different parents, so they are different commit
objects with different IDs:

```text
* <H'> (HEAD -> feature) H: Add more printing
* <G'> G: Make print fancy
* <I> (main) I: Update readme
*   <F> F: Merge branch 'fix'
```

Now `main` points to `I`, while `feature` points to `H'`. Following the parents
from `H'` leads through `G'` to `I`, so the history from `main` is already
included in `feature`. Git can therefore fast-forward `main` by moving its
pointer from `I` to `H'`:

```sh
git switch main
git merge feature --ff-only
git branch -d feature
```

Now `main` points at the same commit `feature` pointed at:

```text
* <H'> (HEAD -> main) H: Add more printing
* <G'> G: Make print fancy
* <I> I: Update readme
*   <F> F: Merge branch 'fix'
```

### Conflicts

Sometimes two branches change the same part of the same file and Git cannot
choose the right answer by itself. The last part of `git-101.sh` starts setting
up that situation:

```sh
git switch -c hotfix
```

Add a new first print line:

```diff
 def main():
+    print("Hello, hotfix!")
     print("Hello, git!")
     print("Hello, rebase!")

 if __name__ == "__main__":
     main()
```

Stage and commit it:

```sh
git add -A
git commit -m "J: Hotfix main"
```

Back on `main`, add a different first print line in the same place:

```sh
git switch main
```

```diff
 def main():
+    print("Hello, world!")
     print("Hello, git!")
     print("Hello, rebase!")

 if __name__ == "__main__":
     main()
```

Stage and commit that change:

```sh
git add -A
git commit -m "K: Add even more printing"
```

At this point, `hotfix` and `main` both inserted a different line in the same
place. If you run `git merge hotfix`, Git will stop and ask you to resolve the
conflict. This is called a _merge conflict_. That is not Git being broken; it
is Git refusing to guess.

```sh
git merge hotfix
```

```text
Auto-merging src/main.py
CONFLICT (content): Merge conflict in src/main.py
Automatic merge failed; fix conflicts and then commit the result.
```

Git has not created a merge commit yet. Instead, it has left the repository in
the middle of the merge so you can decide what the combined content should be.
`git status --short` marks the file as unmerged:

```sh
git status --short
```

```text
UU src/main.py
```

Here, `UU` means that both branches modified the file and it still has an
unresolved conflict. Git writes conflict markers around the part it could not
combine:

```python
def main():
<<<<<<< HEAD
    print("Hello, world!")
=======
    print("Hello, hotfix!")
>>>>>>> hotfix
    print("Hello, git!")
    print("Hello, rebase!")

if __name__ == "__main__":
    main()
```

The content between `<<<<<<< HEAD` and `=======` comes from `HEAD`, which is
our current `main` branch. The content between `=======` and `>>>>>>> hotfix`
comes from the branch we are merging. Depending on your Git configuration, you
might also see a section beginning with `|||||||` that shows the common
ancestor's version.

Resolving a conflict means editing the file into the result you actually want,
including removing the marker lines. You can choose one side, combine both, or
write something else entirely. For this example, keep both greetings:

```python
def main():
    print("Hello, world!")
    print("Hello, hotfix!")
    print("Hello, git!")
    print("Hello, rebase!")

if __name__ == "__main__":
    main()
```

Review the result, then stage the file to tell Git that the conflict is
resolved:

```sh
git diff
git add src/main.py
git diff --staged
```

The staged diff shows the combined result that the merge commit will contain:

```diff
diff --git a/src/main.py b/src/main.py
index c22f971..a26a73b 100644
--- a/src/main.py
+++ b/src/main.py
@@ -1,5 +1,6 @@
 def main():
     print("Hello, world!")
+    print("Hello, hotfix!")
     print("Hello, git!")
     print("Hello, rebase!")
```

Finish the merge by creating the merge commit:

```sh
git commit -m "L: Resolve competing greetings"
```

```text
*   <L> (HEAD -> main) L: Resolve competing greetings
|\
| * <J> (hotfix) J: Hotfix main
* | <K> K: Add even more printing
|/
* <H'> H': Add more printing
```

Like commit `F`, commit `L` has two parents. Both lines of development are now
part of `main`, so the temporary branch name can be deleted:

```sh
git branch -d hotfix
```

If you instead want to abandon a conflicted merge and return to the state from
before `git merge`, run `git merge --abort` before creating the merge commit.
